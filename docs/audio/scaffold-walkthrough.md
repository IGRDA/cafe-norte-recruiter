# Scaffold walkthrough (audio script)

The spoken version (mp4, generated with macOS `say` from this text) is attached to the pull
request that introduced the scaffold, not committed here. About twelve minutes. It covers the decisions and their trade-offs, then every package and the
interfaces it exposes, then evaluation and infrastructure.

---

Hello. This is a walkthrough of the Café Norte recruiting agent repository at its first commit: the scaffold. Nothing here serves a conversation yet. What exists is the shape of the system: the module boundaries, the contracts between them, the fakes that make it testable, the decision log, and the infrastructure outline. I will go through the decisions first, because everything else follows from them, then through each package and its interfaces, then through evaluation and deployment.

Part one. The decisions.

The product is Ana, a bilingual voice and text assistant for a fictional coffee chain. A candidate asks about a barista role, gives their details in any order, corrects them, and confirms a simulated interview slot. The output is a candidate-confirmed brief, a JSON record of the session, and evidence of how the system behaved. The constraints are twenty hours of work and one hundred euros of spend.

Decision one, the most important one: who owns the language model loop. Every turn does the same thing: assemble the prompt, stream the model, validate and run tool calls, at most four rounds, then stream the answer. Both channels need it: voice through Pipecat, and text through HTTP. The spec suggested letting Pipecat own the loop with its Groq service and function registration. We chose the opposite. Our own conversation runtime owns the loop, depends on a Model protocol and a typed tool registry, and Pipecat is only the voice shell: Daily transport, voice activity detection, Deepgram speech to text, ElevenLabs text to speech, and one bridge processor in the middle. The trade-off: Pipecat would have given us tested interruption handling and function streaming for free. In exchange, we would have had the bounded tool loop and the rule "validate before execute" living inside framework callbacks, and loop tests depending on Pipecat's pipeline harness. With our own runtime, the whole agent runs against a fake model in milliseconds, both channels share one code path, and the model adapter from the reference project ports unchanged. The risk we accepted is barge-in: our bridge must honour Pipecat's interruption frames and report what was actually delivered. The voice adapter is kept thin so that, if the hosted checkpoint shows barge-in is too hard, switching voice only to Pipecat's model service touches one package.

Decision two: the browser is vanilla JavaScript modules, no build step. The spec said React, TypeScript and Vite. We chose one toolchain: Python. The cost is hand-rolled rendering for the brief, the confirmation cards and the reviewer panel, and no TypeScript. The benefit is one Docker stage, no Node job in continuous integration, and no second lockfile.

Decision three: Postgres access is psycopg three with numbered SQL migration files, not SQLAlchemy and Alembic. The reason is that the hard requirements are SQL-shaped: ownership leases with generations, admission counted in rows, row-locked slot reservations, idempotency keys, conditional updates on a revision number. An ORM puts a layer between the invariant and the statement that enforces it. The cost is no autogenerate and no Alembic directory for reviewers to recognise. A side effect: the Cloud SQL Python connector does not support psycopg, so Cloud Run connects through its built-in Cloud SQL Unix socket instead. That is decision seventeen.

Decision four: the package layout. The spec's seven modules, plus a separate model package so the runtime depends on a protocol rather than on Groq, plus one central errors module so public error text lives in one place. Every package exposes a contracts file; adapters stay private; an architecture test reads the imports of every source file and fails on a forbidden one.

Decisions five and six: observability and evaluation. Production traces go through OpenTelemetry to Langfuse in the EU region, metadata only by default. The same platform holds evaluation datasets, experiment runs and rubric judges, so traces, scores and prompt versions line up on one screen. For evaluation we keep our own typed runner, because the acceptance criteria are deterministic: recall at three, abstention, zero cross-store leakage, exact extraction, booking invariants. Ragas adds standard retrieval metrics on the twenty-four question set. A judge is a secondary signal and never decides pass or fail. Deepeval and promptfoo were declined as overlap.

Decision seven: deployment is automatic on every push to main. My recommendation was a manual button with environment approval, because of the budget ceiling and the fixed demo window. The owner chose automatic for a tighter loop during the one-week build. The workflow ignores documentation changes, never overlaps runs, and uses a GitHub environment that can get a required reviewer later without changing the workflow.

Decision eight: the specification is committed in a sanitised copy, with the sentences referring to confidential interview material removed and an amendments table at the top that says where the spec text is overridden.

Decisions nine and ten: data modelling. Every record is a frozen Pydantic model that forbids extra keys; every port is a Protocol; enums are Literal unions; domain refusals come back as a small Result type instead of exceptions. The payoff is that the export JSON schema and the tool JSON schemas are generated from the same models the runtime uses. And a candidate field is a discriminated union: Unset, Captured, Confirmed, Unknown, Declined. Only Captured and Confirmed carry a value and evidence. That makes "never fill an unknown field with a guess" a type error rather than a runtime check.

Decision eleven: the text channel uses server-sent events for server to browser, with sequence numbers and replay from Last-Event-ID, and one POST per turn carrying an input identifier and the expected revision. The spec said WebSocket. Reconnect and replay come with the protocol, the POST maps exactly onto "acknowledged once or safely resubmitted", and cookie authentication is identical to every other endpoint.

Decision twelve: prompts are versioned files in the repository with a prompt version constant that is stamped on every session and every evaluation run. Reproducible from a commit, works offline.

The remaining decisions are about this first commit: contracts and fake signatures only; scenarios driven by scripted turns in continuous integration and by a simulated candidate in live runs; every dependency locked now behind optional extras for voice and knowledge; and Postgres-backed tests that skip unless a test database URL is set, so the default check stays offline.

Part two. The packages and their interfaces.

Start with errors. It defines the two supported languages, the stable error codes, the fixed public messages in Spanish and English, and ServiceError, which carries an internal detail and a public code separately so the string of an exception never reaches a candidate or a log.

Domain is pure. No input or output, no clock, no model; time is an argument. Its contracts file holds the identifiers, the enums, the field union, the candidate record with one discriminated union per field, the candidate patch the model may propose, the confirmation record with its target and status, interview slots and bookings, review flags and signals, the store configuration, and the session state. The fields module implements the transitions: capture, confirm, mark unknown, decline, value of. These are the only functions with bodies in the whole scaffold, and property tests pin their laws: capture always yields the new value and drops a stale confirmation; confirm succeeds only from captured; only captured and confirmed carry a value. The other domain files are signatures: validate and apply a patch, find unfinished fields, render the deterministic brief, present a confirmation and interpret an answer against it, the five conditions a reservation needs as one total function, and lifecycle transitions.

Model defines the port the runtime talks to. A ToolSchema is JSON schema generated from the tool's argument model. A ToolCall is fully assembled, never a fragment. The stream method takes messages, tool schemas and a deadline, and yields text deltas, tool calls, optional usage, then one finished event. Adapters: a fake that replays scripted events, and a streaming chat completions adapter for Groq, ported from the reference project. Switching from the one hundred and twenty billion model to the twenty billion one is configuration.

Knowledge holds documents with front matter, chunks by heading, a versioned index manifest, and the Retriever port. Retrieve takes a query with the configuration id and knowledge base version, filters before ranking, fuses BM25 and dense cosine by reciprocal rank, and returns at most three chunks, possibly none. A fake retriever answers from canned results.

Observability defines the version stamp attached to every session and evaluation run: configuration, knowledge base, prompt, schema, model, voice and commit. It defines stage timings with their source, so browser and server clocks are never subtracted; usage records for tokens, characters, seconds and participant minutes; a versioned price table; and cost estimates that list unpriced kinds instead of counting them as zero.

Persistence defines repository protocols: sessions with a conditional save on revision; turns unique per session and input id; events with a sequence number; a calendar whose reserve method is row-locked, unique per slot, idempotent by key; leases with generations; admission; summary jobs; resume tokens stored as hashes; and export snapshots. A Store bundles them with a transaction context. The export module defines ExportDocument, the published JSON schema, with session, candidate, transcript, confirmations, booking, review flags, retrieval events, signals, summary, metrics and versions. There is a Postgres implementation signature and an in-memory one for tests.

Conversation is the runtime. TurnInput is one finalized user turn with an input id. The runtime emits typed events: turn started, assistant text with a spoken form, tool started and finished, state updated after the commit, sources shown, turn finished with usage and timings, or turn failed with a public code. The tools module is the allowlist: nine names, one Pydantic argument model each, and the schemas generated from them. Session, configuration, authorization and idempotency are never arguments; the server injects them through a tool context. The registry validates arguments and allows one repair per turn. The runtime class owns the bounded loop, deadlines, cancellation, and the rule that nothing is announced before it is persisted.

Voice is the Pipecat shell. Contracts define a private room with a bot token that never leaves the server and a short-lived candidate token, a voice status, browser-observed timings, a room provisioner port and a session controller port. The bridge is the only Pipecat-aware class; Pipecat itself is an optional extra and nothing outside this package imports it.

The API package has the request and response models and the session event envelope with its sequence number. Routes are built from ports, so the application is wired once, in main, which reads the environment and names every concrete adapter. With no environment, everything is a fake.

Part three. Evaluation and infrastructure.

Evaluation has three suites. Scenarios S01 to S18, each with scripted turns for the deterministic gate and a persona for the live simulator. Retrieval with twenty-four fixed questions. And the bounded model comparison: six cases, two models, two repetitions. Scorers are pure functions over the export document. Reports carry denominators and the version stamp. Continuous integration runs only the fake mode; live runs are manual and paid.

Infrastructure is two Terraform stacks: bootstrap for the state bucket and the GitHub identity federation, and app for everything the demo needs, with the image digest as an input so a deployment is a Terraform change. Both validate today with their resources outlined as comments. Continuous integration runs lint, strict typing, offline tests, Postgres tests against a service container, and Terraform validation. The deploy workflow builds and pushes the image by digest, applies Terraform, will run migrations, and smoke-checks the service.

That is the scaffold. The next step is the first deep module, the domain, because every other stage depends on it and it needs no credentials; then the hosted voice checkpoint. Thank you for listening.
